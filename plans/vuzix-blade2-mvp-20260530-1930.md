# Vuzix Blade 2 OpenJarvis v1 MVP

## Goal

Prove the full voice→Claude→HUD→TTS loop on the Blade 2 eyepiece, reusing all existing OpenJarvis plumbing, by adding one WebSocket endpoint to jarvis-gateway and one Kotlin Android app.

## Context

- jarvis-gateway is Express/HTTP on port 22100, already speaks `stream-json` from `claude -p --resume`, has Bearer token auth, per-channel warm session cache, and ANSI-aware output. No WebSocket dependency today.
- `src/voice/stt.js` already multi-provider (Deepgram + faster-whisper on generic:8765). The Blade will POST raw audio to faster-whisper directly — same host, same port, no code change needed.
- `src/piper-server.js` is a 213-line HTTP TTS server. Blade POSTs text, gets an audio file back. No changes needed.
- `src/mobile-mode.js` is a toggle flag, not a display layer — it's irrelevant to the Blade display. We do NOT use it.
- The gateway's `/v1/chat/completions` endpoint is the clean reuse target. It already handles: channelKey-scoped session lookup, `--resume <chatId>`, lock serialization, and stream-json output. The Blade relay is a WebSocket wrapper around this same logic — we do not duplicate session management.

## Architecture decision: WebSocket over SSE on the gateway

**Chosen: add a `ws` WebSocket server sharing the existing Express HTTP server** (via `server.on('upgrade', …)`). One new npm dep (`ws`). No second port.

Why WS over SSE:
- Android OkHttp has a mature, battle-tested WebSocket client. Android's `EventSource` is not in the standard SDK — it requires a third-party lib too, so SSE saves nothing on the client side.
- WS is bidirectional: the Blade can send the text prompt, approval responses (`yes`/`no`), and control signals (`stop`, `new-session`) over the same connection. SSE is send-only from server to client — you'd need a second HTTP POST channel for input, making the protocol awkward.
- The gateway already streams partial JSON tokens; WS forwards them as text frames with zero buffering overhead.

**Blade → gateway transport:** `wss://generic.fin-snares.ts.net:22100/v1/blade` over Tailscale. Auth: same `JARVIS_GATEWAY_TOKEN` sent as a query param on the WS handshake URL (standard pattern for WS auth since you can't set custom headers on the Android `WebSocket` constructor directly, though OkHttp does support headers — use header, not query param, to avoid token in logs).

## Approach

### Server side (jarvis-gateway — new `/v1/blade` WS endpoint)

1. Add `ws` npm package to jarvis-gateway.
2. On HTTP server `upgrade` event, route `/v1/blade` path to a `WebSocket.Server` (handleProtocols upgrade pattern).
3. On WS connect: authenticate Bearer token from `Authorization` header (OkHttp sends headers on upgrade). Assign a stable `channelKey` = `agent:main:blade:session:<uuid>` — the gateway's existing `getOrCreateChatId` handles the rest.
4. On WS message from Blade: JSON frame `{ type: "prompt", text: "…" }`. Gateway calls the same `spawnClaudeStream` logic as `/v1/chat/completions`, streaming partial tokens back as WS text frames: `{ type: "token", text: "…" }`.
5. Control frames from Blade: `{ type: "stop" }` → kill the active claude process for this session. `{ type: "new-session" }` → rotate the chatId (same as the existing session rotation logic). `{ type: "approve" }` / `{ type: "deny" }` → inject "yes"/"no" into the claude stdin for tool approval prompts.
6. When claude exits: send `{ type: "done", fullText: "…" }` frame. Gateway passes `fullText` to `postSpeakSummary` — TTS fires on the server side through `piper-server`, played back through the bot's voice channel or returned as a URL the Blade fetches and plays locally (see TTS section below).
7. Strip ANSI escape codes from all token frames before sending (reuse the existing `stripAnsi` utility already present in the gateway's output handling).

### Client side (Kotlin Android app — `JarvisBladeApp`)

**Project setup:** Android Studio project, minSdk 30 (API 30 = Android 11, matches Blade 2), target 34. Single activity (`MainActivity`), no fragments. Declare `RECORD_AUDIO`, `INTERNET` permissions.

**Key libraries (all stable, well-maintained):**
- `com.squareup.okhttp3:okhttp:4.12.0` — HTTP + WebSocket client
- `com.squareup.okhttp3:okio:3.9.0` — bundled with okhttp
- `org.json:json:20240303` — JSON parsing (no Gson/Moshi overhead for this simple protocol)

**Activity lifecycle:**
```
onCreate → connect WS → wait for CONNECTED event → ready
touchpad tap (KeyEvent.KEYCODE_DPAD_CENTER or Vuzix gesture) → startRecording()
touchpad release → stopRecording() → postAudioToSTT() → sendPrompt(text)
WS token frames → appendToHUD(text) → renderHUD()
WS done frame → fetchAndPlayTTS(audioUrl)
```

**Touchpad:** The Blade 2 touchpad fires standard Android `KeyEvent`. Map `KEYCODE_DPAD_CENTER` (swipe tap) to push-to-talk. No Vuzix SDK required for v1 — standard Android input events work.

**Audio recording:** `android.media.MediaRecorder` → output format `MPEG_4`, encoder `AAC`. POST the file to `http://generic.fin-snares.ts.net:8765/transcribe` (faster-whisper HTTP API). Parse response JSON `{ text: "…" }`. On failure: show "STT failed" on HUD, do not send to gateway.

**STT circuit-breaker:** Implement the same 3-strikes pattern from `src/voice/stt.js`: if 3 consecutive STT calls fail within 60s, show "STT offline" on HUD and skip recording until the next tap (reset on success).

### HUD layout — the 480×480 constraint

One `TextureView` or `SurfaceView`, full screen. Render via `Canvas` + `Paint`, not XML layouts. Why: we need full control over font metrics and can't trust standard Android view padding on the monocular display.

**Layout zones (portrait 480×480):**
```
┌─────────────────────────────┐  y=0
│  STATUS BAR  (32px tall)    │  "● CONNECTED  model: opus"
│  single line, small font    │
├─────────────────────────────┤  y=32
│                             │
│   SCROLL AREA (352px)       │  last N lines of claude output
│   monospace, ~22px/line     │  ~16 lines visible
│   word-wrap at ~28 chars    │
│                             │
├─────────────────────────────┤  y=384
│  PROMPT BAR  (48px tall)    │  "Listening…" / "Thinking…"
│  bright accent color        │  or confirmation: "approve? YES/NO"
│  large font, always visible │
│                             │
└─────────────────────────────┘  y=480
```

Font: `Typeface.MONOSPACE`, 22sp for scroll area, 18sp for status, 26sp for prompt bar. Color scheme: black background, white text, green accent for prompt bar, yellow for status.

**Rendering:** Token frames append to a ring buffer of 200 chars per line, max 16 lines. On each `token` frame, trim to last 16 lines, call `invalidate()` on the view. `onDraw()` renders all lines bottom-up from the prompt bar upward. This means latest output is always at the bottom — natural terminal feel.

**Word wrap:** Simple: split text into 28-char chunks before adding to the line buffer. No hyphenation, just hard wrap. At 22sp monospace on 480px, 28 chars fits comfortably.

### TTS — voice reply

Two options evaluated:
1. **Server-side TTS, audio streamed to voice channel** — gateway POSTs summary to piper-server, plays through the Discord voice channel. Blade hears it through the room speaker or its own mic pickup. Works today, zero Blade code.
2. **Client-side TTS, Blade fetches audio** — gateway returns an audio URL in the `done` frame, Blade's `MediaPlayer` fetches and plays through the Blade speaker.

**Chosen: option 2 (client-side, Blade speaker).** Reason: hands-free, ear-only experience. The Blade speaker is on your head. Room audio means you need to be near a speaker and it leaks sound to the environment. The gateway already has piper-server running — we just expose the generated audio as a URL and the Blade fetches it.

Implementation: when `done` frame arrives, gateway generates TTS via piper-server, saves to a temp file under `/tmp/blade-tts-<uuid>.wav`, serves it at `http://generic:22100/v1/blade/tts/<uuid>` (new GET route, auth required). Blade's `MediaPlayer` plays it. File deleted after 60s.

### Approval UX

When claude output contains a tool-use confirmation pattern (detected by the gateway scanning the raw stream for `[Y/n]`, `Approve?`, `allow`, `deny` keywords in the partial token stream), gateway sends a special frame: `{ type: "approval", prompt: "Edit brain.js — approve?" }`. Blade renders this in the prompt bar with `[TAP=yes  SWIPE=no]` hint. Tap = sends `{ type: "approve" }`. Long swipe left = sends `{ type: "deny" }`. No voice grammar needed for v1 — gestures are faster.

## Risks

- **Vuzix touchpad KeyCode mapping** → test first with `adb shell getevent -l` while tapping to confirm actual keycodes on Blade 2 hardware before wiring gestures
- **faster-whisper audio format** → verify it accepts AAC/MP4 (it does per docs; fallback: record as WAV/PCM if not)
- **piper-server audio format** → it returns WAV; Android `MediaPlayer` handles WAV natively, no transcode needed
- **Tailscale on Blade 2** → Tailscale has an Android app; install it on the Blade via ADB sideload if not on Play Store. Alternatively, use the LAN IP (`192.168.1.90:22100`) for home-WiFi-only v1 and add Tailscale in Phase 5.
- **WS auth header on Android WebSocket constructor** → OkHttp supports headers on WS upgrade (unlike browser `WebSocket`). Use `Request.Builder().header("Authorization", "Bearer …")`. Do not put token in URL query param.
- **Gateway running as `127.0.0.1` only** → currently `app.listen(PORT, "127.0.0.1", …)`. WS from Blade needs the gateway accessible on the Tailscale interface. Change listen address to `0.0.0.0` (or bind to Tailscale IP specifically) when deploying the WS endpoint. Firewall via token auth, not bind address.
